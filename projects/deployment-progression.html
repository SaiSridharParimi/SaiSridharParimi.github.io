Deployment Progression

The same TypeScript + Postgres stack deployed three ways - each stage solving the problem the previous one exposed.

  • Docker
  • Docker Compose
  • Turborepo
  • pnpm workspaces
  • Prisma
  • Next.js
  • Express
  • WebSockets
  • nginx
  • pm2
  • GitHub Actions
  • Docker Hub

Problem

The application is intentionally small - an HTTP API, a WebSocket server, a Next.js frontend, and one Prisma schema - so the focus is the deployment. The questions: how do you get schema migrations, multiple services, and repeatable builds onto a server without running anything by hand, and what does each approach cost?

Approach / architecture

Stage 1 - Single service in a container (be-docker)

  1. Imagenode:22-alpine; dependencies installed, Prisma client generated, and TypeScript compiled at build time.
  2. Migrate on startAn entrypoint runs prisma migrate deploy before starting the server, so the schema is always current before the first request.
  3. ComposePostgres and the backend on a user-defined bridge network, with the app reaching the database by service name.

Next challenge: multiple services and automated delivery to a server.

Stage 2 - Monorepo with CI/CD (app-deploy)

  1. MonorepoTurborepo + pnpm workspaces: a Next.js web app, an Express HTTP API, a WebSocket server, and a shared @repo/db package that exports one Prisma client to all three.
  2. Continuous deploymentOn push to main, GitHub Actions connects to the staging VM over SSH, pulls the latest code, bootstraps the toolchain, runs migrations, builds, and restarts each app under pm2.
  3. Routingnginx serves one subdomain per app (frontend, HTTP API, WebSocket) as a reverse proxy, with the upgrade headers WebSockets need.

Next challenge: builds ran on the server, so every server needed the full toolchain and releases depended on its state.

Stage 3 - Dockerized monorepo (monorepo-docker-deployment)

  1. One Dockerfile per appWorkspace manifests and shared packages are copied and installed before each app's source, so dependency layers are reused across builds.
  2. Build once in CIGitHub Actions builds the HTTP, WebSocket, and frontend images and pushes them to Docker Hub, tagged with the commit SHA.
  3. Deploy by pullingA deploy job, gated on a successful build, pulls the exact SHA-tagged backend images on the VM and replaces the running containers.
  4. Migrations at start-upEntrypoints apply pending migrations with prisma migrate deploy before starting each service.
  5. Local parityA Compose file runs all three apps plus Postgres with a persistent volume on one network.

Key decisions & tradeoffs

Build artifacts once, run them anywhere

Moving builds from the server into CI means the server only needs Docker. Tagging images by commit SHA ties every running container to an exact commit, and rolling back is just pulling an earlier tag.

One shared database package

A single Prisma package in the monorepo gives all three apps the same schema and generated types, so a schema change is one change, type-checked everywhere it's used.

Migrations as part of start-up

Running prisma migrate deploy in each entrypoint keeps deploys to a single step and guarantees the schema is current before traffic arrives. The tradeoff is coupling start-up to the database being reachable.

Simplicity over zero downtime

Stage 3 replaces containers stop-then-start, which is simple and fine for one VM but leaves a brief gap per deploy. Rolling, zero-downtime releases are covered in the AWS platform project.

Results

  • 3deployment stages, each building on the last
  • 3images built and versioned per commit
  • 1shared Prisma package across 3 apps
