Zero-Downtime AWS Web Platform

Every merge to main bakes a new machine image and rolls it across an auto-scaling group behind a load balancer, keeping at least 90% of capacity healthy throughout.

Two repositories: tf-aws-infra (Terraform for the environment) and webapp (the Node.js service, its tests, and the build/deploy pipeline).

Problem

Deploying a web API by hand to a single VM - copy a build over SSH, run a setup script - makes every release a manual step and a moment of downtime, and the server's state drifts from what's in the repo. The goal was to declare the whole environment in code, make releases immutable, and replace servers without dropping traffic.

Approach / architecture

Request path

  1. Route 53 → Application Load BalancerAn alias record points the domain at an internet-facing ALB across three subnets. HTTPS uses an ACM certificate with a TLS 1.3 security policy.
  2. Target group → Auto Scaling group3-5 instances on port 8080. ELB health checks call /healthz, which verifies the database connection, so an instance that can't reach RDS is taken out of rotation.
  3. App → RDS and S3Express + Sequelize. /v1/file uploads files to S3 and stores their metadata in RDS (MySQL 8.0 in private subnets, not publicly accessible).

Release path

  1. Pull request checksAPI tests (Jest + supertest) against a MySQL 8.0 service container, plus packer validate and terraform fmt/validate.
  2. Bake the AMI on mergePacker builds from Ubuntu 24.04: installs Node 18 and the app, creates a dedicated service user, and installs a systemd unit and the CloudWatch agent.
  3. Share across accountsThe pipeline waits for the image to become available, then shares it from the dev AWS account with the demo account.
  4. New launch template versionCreated from the latest version with only the image ID changed.
  5. Rolling instance refreshMinimum 90% healthy, 300 s warm-up per instance. The workflow polls the refresh and fails the run if it doesn't complete successfully.

Key decisions & tradeoffs

Immutable images over in-place deploys

Nothing is installed on a running server. A bad build becomes an AMI whose instances never pass health checks, not a half-upgraded box, and every instance is identical to the tested image. The tradeoff is release speed: a full image build plus a rolling refresh with a 5-minute warm-up per instance.

One image, many environments

The AMI carries no environment-specific values. Terraform's launch-template user data writes the database host, credentials, and bucket name at boot, so the same image runs in both the dev and demo accounts.

Layered network access

Security groups reference each other instead of IP ranges: the ALB accepts 80/443 from the internet, instances accept the app port only from the ALB, and the database accepts 3306 only from the instances. Application instances sit in public subnets, which avoids NAT gateway cost; the security-group chain keeps them unreachable except through the load balancer.

Encryption with separate keys

Four customer-managed KMS keys - EBS volumes, RDS, S3, Secrets Manager - each rotating every 90 days, so access to one data store doesn't imply access to another. The database password is generated by Terraform and stored in Secrets Manager.

Simple, predictable scaling

CloudWatch alarms on average CPU over two 2-minute periods add or remove one instance at a time, with a 60-second cooldown. Small steps make scaling easy to reason about at this traffic level.

Observability from day one

Structured JSON logs ship to CloudWatch Logs through the agent. Every endpoint emits StatsD counters and timers - request counts, S3 upload/delete latency, database query latency - collected by the same agent.
