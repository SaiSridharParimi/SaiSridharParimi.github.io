Cloud IDE

Open a room, share the link, and code together in the browser - same files, same editor, same live bash terminal.

Problem

Remote pairing usually means one person shares a screen while the other watches. Hosted IDEs solve this but hide how they work. This project builds the core loop from scratch: a shared workspace where everyone in a room sees the same files, can edit, and can run commands in a terminal that executes on the server.

Approach / architecture

  1. AccountsSign-up and sign-in over REST. Passwords are hashed with bcrypt; sign-in returns a JWT plus a user slug, which the client verifies with the server before entering a room.
  2. Arenas and rooms"Create Arena" creates an arena and its room in Postgres (Prisma models User, Arena, Room) and returns a short shareable slug. The arena URL is the invite link.
  3. PresenceJoining puts the socket in a Socket.IO room named after the slug and records membership in the database. Members get live join/leave events, and the header shows an avatar for each person in the room.
  4. Terminalnode-pty spawns a real bash shell. xterm.js keystrokes stream up over the socket and terminal output streams back.
  5. Files and editorThe server serves a recursive tree of the workspace. Monaco picks syntax highlighting from the file extension, and edits auto-save over the socket after a 2-second pause.
  6. Live file treechokidar watches the workspace, so any change - from the editor or from a command like touch in the terminal - pushes a refresh to connected clients.

Key decisions & tradeoffs

A real PTY instead of a simulated shell

Using node-pty means prompts, colors, and interactive programs behave like a local terminal. Combined with the file watcher, one mechanism keeps the file tree in sync whether files change from the editor or the shell.

Debounced auto-save

Saving two seconds after typing stops keeps socket traffic low and avoids writing to disk on every keystroke. The tradeoff is that concurrent edits to the same file resolve as last-write-wins.

Stateless auth, persisted rooms

JWTs keep authentication stateless, while room membership lives in Postgres so the member list can be queried over REST (/room/users) as well as pushed over sockets.

Next steps

Per-room sandboxing (a container and workspace per arena), scoping terminal and file events to each room, and real-time co-editing with a CRDT such as Yjs.
