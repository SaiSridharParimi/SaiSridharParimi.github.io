Multi-Domain Intent Classification

One fine-tuned DistilBERT that routes both banking requests and everyday assistant requests - 93.8% accurate on in-scope queries, with 228 classes including out-of-scope.

  • DistilBERT
  • Hugging Face Transformers
  • PEFT / LoRA
  • scikit-learn
  • Streamlit

Problem

A bank's assistant gets two kinds of messages: domain-specific ones ("my card payment was declined") and general ones ("set an alarm for 7am"). Running a separate classifier per domain means deciding which model to call before you know what the user wants. The goal was a single classifier over both label spaces that also recognizes when a request is out of scope.

Approach

  1. Merge two public datasetsBanking77 (13,083 queries, 77 intents) and CLINC150 "plus" (23,850 queries, 150 intents + out-of-scope). Labels are namespaced banking_N / clinc_N to give 228 classes.
  2. Clean and de-duplicateLower-casing and contraction expansion, then removal of 208 duplicate texts → 36,725 samples.
  3. Split, stratified by labelTrain 23,996 · validation 4,235 · test 8,494. The test set is held out entirely from model selection.
  4. Fine-tune and sweep the learning ratedistilbert-base-uncased (67.1M params), max length 128, batch 32, 5 epochs, warmup 10%, weight decay 0.01, best checkpoint by validation F1. Three runs: LR 1e-5, 2e-5, 5e-5.
  5. Parameter-efficient variantA LoRA adapter (r = 8, α = 16 on the attention query/value projections) trains 913,380 parameters (1.34% of the model), cutting training time by 66% and memory by 75%, with a 2 MB adapter instead of a 256 MB model.
  6. Evaluate rigorouslyAccuracy, weighted and macro F1, a bootstrap confidence interval, a McNemar significance test against a majority-class baseline, and error analysis by class, domain, query length, and scope.
  7. ServeA Streamlit app returns the top-k intents with confidences, plus a batch mode with CSV export.

Key decisions & tradeoffs

One label space instead of a domain router

A single model is simpler to serve and avoids a routing step that can itself be wrong. The risk is that overlapping intents in the two datasets (balance, transfer, card issues) compete. The error analysis tests this directly: only 8.7% of errors land in the wrong domain.

Learning rate was the lever that mattered

At 1e-5 the model was still under-fit after 5 epochs (74.9% accuracy). 5e-5 converged fastest of the three runs and scored best, so it became the served model.

Reporting in-scope and out-of-scope separately

Recognizing "none of the above" is a different task from choosing among known intents, so a single accuracy number hides what the model is doing. Splitting the test set by scope shows the classifier is strong on real intents and conservative about rejecting them.

Domain-aware re-ranking in the demo

The Streamlit app gently boosts banking intents (×1.15) when a query contains banking keywords like "account" or "card", which helps the overlapping intents in an interactive setting. Reported metrics are from the model alone.

Error analysis

  • Only 20 of 7,494 real requests are wrongly rejected as out-of-scope.
  • Of all errors, 8.7% cross domains (banking ↔ general); the merged label space holds up.
  • Error rate by length: 9.5% for 1-5 words, ~10.4% for 6-20 words, 6.4% for 20+ words - longer queries carry more signal.
  • The largest single error source is out-of-scope queries being matched to a real intent, which points to the next step below.

Next steps

Add a confidence threshold that routes low-confidence predictions to out-of-scope, tuned on the validation set to trade OOS recall against false rejections. Then evaluate the LoRA adapter's accuracy against the fully fine-tuned model to decide which one to serve.
