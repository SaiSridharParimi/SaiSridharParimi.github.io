Patient Management Microservices Course project

Five Spring Boot services behind one gateway, using a synchronous gRPC call where the caller needs an answer and a Kafka event where it doesn't.

  • Java 21
  • Spring Boot 3.4
  • Spring Cloud Gateway
  • gRPC / Protobuf
  • Kafka
  • PostgreSQL
  • JWT
  • Docker
  • OpenAPI

Problem

Registering a patient touches several concerns: the patient record, a billing account, and analytics. In a monolith these are coupled in one codebase and one deploy. This project splits them into independently deployable services and works through how each pair should communicate.

Approach / architecture

  1. API gatewaySpring Cloud Gateway is the single entry point. It routes /auth/** to auth-service and /api/patients/** to patient-service, and a custom JWTValidation filter validates tokens with auth-service before forwarding. It also proxies each service's OpenAPI docs.
  2. auth-service/login checks BCrypt-hashed credentials and issues a signed JWT (email + role, 10-hour expiry); /validate verifies tokens for the gateway.
  3. patient-serviceREST CRUD on PostgreSQL with bean validation (including a validation group for create-only fields), duplicate-email checks, and centralized exception handling.
  4. billing-service over gRPCCreating a patient makes a blocking CreateBillingAccount call; deleting one calls DeleteBillingAccount. The contract is a shared .proto file.
  5. analytics-service over KafkaAfter a create, patient-service publishes a Protobuf-encoded PatientEvent to the patient topic, which analytics-service consumes in its own consumer group.
  6. ContainerizedEach service has a multi-stage Dockerfile: a Maven + JDK 21 build stage with dependencies cached as their own layer, then a runtime stage that contains only the built JAR.

Key decisions & tradeoffs

gRPC for billing, Kafka for analytics

Billing setup is one-to-one and the caller needs the result, so it's a synchronous gRPC call with a typed contract and low overhead. Analytics is one-to-many and nobody waits on it, so it's an event. The consequence: patient creation depends on billing being available, while analytics can lag or go down without affecting users.

Protobuf for events as well as RPC

Using Protobuf for the Kafka payload gives producer and consumer one shared schema and compact messages, in exchange for payloads that aren't human-readable in Kafka tooling.

Authentication at the gateway

Downstream services don't parse tokens themselves; the gateway validates once per request. That centralizes security logic in one place, at the cost of an extra network hop on protected calls.

Next steps

A transactional outbox so the database write and the Kafka event can't diverge, and retries with a circuit breaker on the gRPC call to billing.
